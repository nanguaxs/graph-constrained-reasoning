# 关系序列综述

更新日期：2026-04-08

本文聚焦一个比“KG + LLM 推理”更窄、但对当前仓库更关键的问题：

> 在知识图谱问答与图约束推理中，如何高效、准确地获取可执行的关系序列（relation sequence / rule / relation-only path skeleton）？

这里的“关系序列”特指不包含中间实体、只保留关系链骨架的表示，例如：

```json
["people.person.parents", "people.person.children"]
```

对当前仓库而言，这种表示和 `add_rule` 的语义最接近：先预测一条关系序列，再在真实图上展开成可执行路径，然后送入约束解码或最终答题阶段。

## 1. 先给结论

截至 2026 年 4 月 8 日，获取关系序列的主流路线已经从“直接枚举路径”演进为五类互补方法：

| 路线 | 代表工作 | 关系序列的来源 | 优点 | 主要短板 |
| --- | --- | --- | --- | --- |
| 离线规则/片段诱导 | Rule-KBQA, FGSP | 从训练数据、真值路径、语义片段中归纳 | 精度高、成本低、适合做规则库 | 泛化依赖数据覆盖，遇到新 schema 容易掉点 |
| 逻辑形式/骨架优先 | KB-BINDER, ChatKBQA, RGR-KBQA, KaeDe, CoG | 先生成逻辑形式或查询骨架，再抽关系序列 | 可执行性强、结构化好 | 往 relation-only 压缩时会丢失过滤条件和操作符 |
| 在线图搜索/Agent 规划 | ToG, RoG, FiDeLiS, RJE, RouterKGQA | 在搜索过程中逐步选关系、保留 top-k 分支 | 召回高、适合复杂多跳 | 如果没有 verifier，模型调用多、容易偏题 |
| 检索/重排/语义最短路径 | Q-KGR, AMAR, GNN-RAG, S-Path-RAG | 先取相关子图/路径，再压缩成关系序列 | 成本较低，相关性通常优于纯枚举 | 不一定天然输出“规则”，常需二次压缩 |
| 图约束生成/执行 | GCR, DoG | 借助合法路径空间约束生成 | faithfulness 强、路径可追踪 | 更像“执行器”，不是最强的关系序列规划器 |

如果只看“前沿趋势”，最新公开工作的重点已经很明显：

- 2025 年开始，主线从“只保合法”转向“合法 + 相关 + 可验证 + 可修正”。
- 2026 年 3 月公开的预印本进一步强调低调用成本路由、合成轨迹课程学习、强化学习和语义最短路径检索。
- 对当前仓库最有现实价值的，不是单独押注某一类方法，而是把“关系序列获取”拆成 `候选生成 -> 重排/验证 -> 图上执行` 三层。

## 2. 为什么“关系序列”比完整路径更值得单独讨论

完整路径当然信息更全，但 relation-only sequence 有几个独特优点：

- 它更稳定。实体会随题目变化，但关系模板可复用。
- 它更便于建规则库。可以离线积累、聚类、统计频率、做人审。
- 它更适合作为中间规划层。先定“走哪些关系”，再去图里展开真实实体路径。
- 它更容易和当前仓库的 `bfs_with_rule()`、`add_rule`、`GCR trie` 等组件对接。

但它也有天然缺陷：

- 丢失方向、类型约束、比较符、聚合符、时间过滤等逻辑信息。
- 不同实体路径可能压缩成同一条关系序列，导致歧义。
- 对 CVT、中介节点、逆关系或属性值节点较多的数据集，relation-only 序列往往不够表达完整查询意图。

因此，当前最有效的方法通常不是“只要关系序列”，而是“先得到高质量结构骨架，再在执行阶段补回方向、类型和实体约束”。

## 3. 方法谱系

### 3.1 从数据中直接诱导规则或关系片段

这条路线最适合“想要一个可复用的 relation sequence 库”。

Rule-KBQA（COLING 2025）把规则作为显式中间层，先诱导与问题匹配的规则，再按规则执行推理。它的价值在于把“可解释规则”和“执行”明确分离，非常适合 relation-only 产物的离线沉淀。缺点是对规则库质量和覆盖率高度敏感。  
链接：<https://aclanthology.org/2025.coling-main.562/>

FGSP（ACL 2025）把复杂语义解析拆成更细粒度的语义片段和子图单元，再组合成最终查询。它不一定直接输出 relation-only 序列，但它特别适合抽出“高质量关系片段”，然后压缩成局部规则。对长链复杂问句，这类方法比直接生成整条关系链更稳。  
链接：<https://aclanthology.org/2025.acl-long.710/>

这类方法的共同优点是：

- 推理时开销小。
- 可维护、可审计。
- 容易和现有 `rule_path` 文件格式对接。

这类方法的共同问题是：

- 数据稀疏时会漏规则。
- 遇到新 schema、新领域、新关系组合时泛化有限。

如果你的目标是“长期积累一个离线规则库”，这条路线是最值得优先布局的。

### 3.2 先生成逻辑形式或查询骨架，再压缩成关系序列

这是目前精度和可执行性最稳的一条线之一。

KB-BINDER（2023）展示了 LLM 先生成结构化表示、再做 schema 绑定与执行的潜力。它更偏零样本语义解析，但对“先出骨架，再绑定具体元素”的思路影响很大。  
链接：<https://arxiv.org/abs/2305.01550>

StructGPT（EMNLP 2023）把 structured data 访问和自然语言推理解耦，强调先读结构、再推理。它不直接输出 rule，但为“骨架优先”的方法奠定了范式基础。  
链接：<https://aclanthology.org/2023.emnlp-main.574/>

ChatKBQA（Findings of ACL 2024）是这条路线在 KGQA 上最典型的代表之一：先生成逻辑形式，再做实体和关系检索与替换。它的优势是生成目标很明确，关系序列可以从逻辑形式主干中抽取出来。  
链接：<https://aclanthology.org/2024.findings-acl.122/>

RGR-KBQA（COLING 2025）把“生成逻辑形式”与“知识图谱增强”结合起来，进一步强调结构化目标的生成质量。  
链接：<https://aclanthology.org/2025.coling-main.205/>

KaeDe（Findings of ACL 2025）通过 knowledge-aware demonstration retrieval 做逐步逻辑形式生成，核心价值是：在生成骨架前先找更像的示例，提高结构稳定性。对 relation sequence 来说，这意味着可以先得到更靠谱的 schema-aligned skeleton，再做压缩。  
链接：<https://aclanthology.org/2025.findings-acl.637/>

CoG（ACL 2025）把 query correcting 显式纳入流程，说明“先生成、再修正”比一次性生成更稳。对关系序列任务，这很重要，因为很多错误不是完全无关，而是“只差一步关系或方向”。  
链接：<https://aclanthology.org/2025.acl-long.1180/>

这一类方法最适合下面两种需求：

- 你希望最终产物可执行率高。
- 你愿意保留比 relation-only 更多的结构信息，再在最后压缩成关系序列。

但也要注意一个关键现实：  
逻辑形式并不等于关系序列。若直接把逻辑形式“砍成关系链”，会丢掉方向、约束和操作符。所以最好的做法通常不是“只保留关系”，而是至少保留：

- 关系名
- 方向
- 必要类型约束
- 可选的终点类型或答案类型

### 3.3 问题分解、本体先验与反向规划

当问题很复杂时，“直接从起点实体向外搜关系”常常不够好，因为模型并不知道目标语义长什么样。

KELDaR（Findings of EMNLP 2024）把复杂问题拆成 decomposition tree，并对叶子问题做 atomic retrieval。对关系序列获取而言，这意味着序列可以先在子问题层面生成，再做组合，而不是一次性压整题。  
链接：<https://aclanthology.org/2024.findings-emnlp.670/>

ORT（ACL 2025）提出 ontology-guided reverse thinking，从目标或答案类型反推需要什么关系链，而不是只做正向扩展。这对于 relation sequence 特别有意义，因为很多序列错误并不是“走错一步”，而是整个目标类型就错了。  
链接：<https://aclanthology.org/2025.acl-long.741/>

这条路线的核心启发是：

- 关系序列不是纯检索问题，而是规划问题。
- 规划如果没有目标语义，关系链容易合法但不相关。
- 把答案类型、本体约束、子问题目标前置，通常比单纯扩大 beam 更有效。

### 3.4 在线图搜索与 Agent 式关系决策

如果不想完全依赖离线规则库，那么在线搜索仍然是获取关系序列最灵活的路线。

ToG（ICLR 2024）把 LLM 当作图上 agent，逐层做关系筛选、实体扩展和 sufficiency 判断。它的优势是关系选择发生在真实图环境里，适合在线规划；缺点是原始实现模型调用多。  
链接：<https://arxiv.org/abs/2307.07697>

RoG（ICLR 2024）提出 planning-retrieval-reasoning 框架，先生成 relation paths 作为 faithful plan，再按 plan 检索真实证据路径。对于“先拿关系序列，再执行”的需求，RoG 的思路非常直接。  
链接：<https://arxiv.org/abs/2310.01061>

FiDeLiS（Findings of ACL 2025）把 step-wise beam search、deductive scoring 和 sufficiency judgment 结合起来，重点不只是“继续扩展”，而是“当前证据是否已经足够”。这对关系序列质量很关键，因为很多冗余错误来自不该继续搜却继续搜。  
链接：<https://aclanthology.org/2025.findings-acl.436/>

RJE（EMNLP 2025）把 Retrieval、Judgment、Exploration 分成三个阶段，只在判断证据不充分时继续扩展。这种“判断后再搜索”的结构，比纯 beam search 更省调用，也更适合 relation sequence 的在线获取。  
链接：<https://aclanthology.org/2025.emnlp-main.873/>

RouterKGQA（arXiv，2026-03-29）是截至目前我查到的一个很值得关注的低成本方向。它通过协作路由来避免在巨大动作空间中反复采样，摘要里直接强调平均只有约 1.15 次 LLM 调用，同时保持较强表现。  
链接：<https://arxiv.org/abs/2603.21717>

GraphWalker（arXiv，2026-03-27）用 synthetic trajectory curriculum 学习 agentic KGQA，本质是在训练中显式教模型“如何走出高质量关系轨迹”。  
链接：<https://arxiv.org/abs/2603.28533>

KG-Hopper（arXiv，2026-03-26）把强化学习引入紧凑开源模型的 KG 推理，强调低成本模型也能学到更好的图上策略。  
链接：<https://arxiv.org/abs/2603.21440>

这条路线目前最前沿的趋势非常明确：

- 不再只靠一次性生成整条链。
- 更强调逐步 relation gating。
- 更强调 verifier / judgment / repair。
- 更强调用课程学习或 RL 学“怎么走图”。

### 3.5 先做高相关检索或重排，再压缩成关系序列

如果你最担心的是效率，这条路线常常比纯 Agent 搜索更实用。

Q-KGR（Findings of EMNLP 2024）先对知识图谱子图做 question-guided re-scoring，再注入给 LLM。它不一定先输出 relation sequence，但它很适合做“候选路径重排”，然后把高分路径压缩成关系链。  
链接：<https://aclanthology.org/2024.findings-emnlp.524/>

AMAR（公开于 2024，AAAI 2025 方向）通过多视角检索和自适应 gating 过滤实体、关系和子图。它对 relation sequence 的价值在于：可以把“关系检索”放到统一的多视角检索框架中，而不是只靠 LLM 单独判别。  
链接：<https://arxiv.org/abs/2412.18537>

GNN-RAG（Findings of ACL 2025）先用 GNN 在稠密子图中做检索，再取最短路径作为证据。它的优点是相关性打分前置，推理时比纯多轮 Agent 便宜。  
链接：<https://aclanthology.org/2025.findings-acl.856/>

S-Path-RAG（arXiv，2026-03-29）把语义感知和最短路径检索结合，明显是在“相关性优先”的 shortest-path 路线上继续推进。  
链接：<https://arxiv.org/abs/2603.23512>

这类方法通常不把“关系序列”当最终学习目标，而是把它视为高质量路径的压缩表示。它们非常适合做当前仓库的前置模块：

- 先取相关子图或候选路径
- 压缩成 relation sequences
- 再交给 `add_rule` 或约束解码执行

### 3.6 图约束解码与图上执行器

这一类工作对当前仓库最相关，但要明确：它们更像“faithful executor”，不一定是最强的 relation planner。

GCR（ICML 2025）用 KG-Trie 在生成时约束 token，只允许输出图中真实可达的路径。它能显著减少幻觉，非常适合作为执行层。  
链接：<https://proceedings.mlr.press/v267/luo25t.html>

DoG（ACL 2025）强调生成 well-formed chains，也是在图约束生成上做强化。  
链接：<https://aclanthology.org/2025.acl-long.1186/>

这两类方法的强项是：

- 路径合法
- 过程可追踪
- 适合作为最终执行器

这两类方法的局限是：

- 不能自动解决“该搜哪条关系序列”
- 如果前置候选空间相关性不好，合法路径里仍然会有大量噪声

所以对“获取关系序列”这个问题，GCR/DoG 更适合放在后端，而不是单独充当前端规划器。

## 4. 从“高效”和“准确”两个维度看当前主流选择

### 4.1 如果你最重视准确率和可执行性

优先考虑：

- ChatKBQA
- KaeDe
- CoG
- RGR-KBQA
- Rule-KBQA

原因是这几类方法更偏结构化规划或可修正的语义解析，得到的骨架通常更接近真实查询意图。代价是实现复杂，且 relation-only 压缩时要小心信息损失。

### 4.2 如果你最重视低调用成本和部署效率

优先考虑：

- Q-KGR
- GNN-RAG
- S-Path-RAG
- RouterKGQA

原因是这几类方法把“关系相关性估计”前移到了检索、路由或重排阶段，通常比 ToG 式多轮 LLM 搜索便宜。

### 4.3 如果你最重视召回和开放式多跳探索

优先考虑：

- ToG
- RoG
- FiDeLiS
- RJE
- GraphWalker
- KG-Hopper

原因是它们更适合“先多拿候选，再验证和收敛”，对复杂多跳尤其有价值。

### 4.4 如果你已经有一个合法执行器，只差一个更好的前端 planner

优先考虑：

- ORT
- Q-KGR
- AMAR
- RJE
- Rule-KBQA
- RouterKGQA

这几类最容易和现有 GCR 组合成两层结构：

`高相关关系序列获取 -> GCR 图上执行`

## 5. 对当前仓库最有现实意义的组合方案

如果目标是给当前仓库的 `add_rule` 找到一条更前沿、但又能落地的路线，我更推荐下面三种组合。

### 方案 A：离线规则库优先

适用场景：固定数据集、希望高稳定性、希望积累 rule。

推荐组合：

- 用 FGSP / KaeDe / ChatKBQA 风格方法得到高质量结构骨架。
- 抽取 relation-only 序列，加上方向和终点类型，形成规则库。
- 用 Rule-KBQA 风格的规则检索或匹配做问题级 top-k 选择。
- 最后交给 GCR 或 `bfs_with_rule()` 展开执行。

优点是稳定、可维护、易做人工分析。缺点是新领域适应慢。

### 方案 B：低成本在线路由

适用场景：不想大量调用大模型，希望在线预测规则。

推荐组合：

- 用 Q-KGR / GNN-RAG / S-Path-RAG 缩小候选子图。
- 用 RouterKGQA 或轻量 relation scorer 对关系序列做路由选择。
- 用 GCR 做图上合法执行。

这条路线很可能是当前仓库最现实的“提效不降太多精度”方案。

### 方案 C：多跳复杂问题的分解式搜索

适用场景：复杂多跳、组合查询、需要高召回。

推荐组合：

- 用 KELDaR 或 ORT 先得到子问题或目标本体约束。
- 用 ToG / RJE / FiDeLiS 风格逐步搜索子问题关系链。
- 用 verifier 判断当前关系链是否已足够。
- 用 GCR 或图执行器落地。

这条路线调用多一些，但对复杂问题上限更高。

## 6. 我对“当前最前沿方向”的判断

结合 2025-2026 的公开论文，我认为“获取关系序列”的最前沿已经不是单点技术，而是四个趋势的叠加：

### 6.1 从一次性生成，转向逐步规划 + 判断 + 修正

ToG、FiDeLiS、RJE、RouterKGQA、CoG 共同说明：  
先拿草案，再判断，再修正，往往比一次性把整条关系链写对更稳。

### 6.2 从纯语言概率，转向问题条件下的相关性模型

Q-KGR、AMAR、GNN-RAG、S-Path-RAG 的共识是：  
关系序列质量的核心瓶颈并不只是“会不会生成”，而是“是不是和问题真正相关”。

### 6.3 从单题在线搜索，转向可迁移的轨迹学习

GraphWalker 和 KG-Hopper 代表的是策略学习路线。它们不只是为一题生成关系链，而是在学“怎样在图上形成好轨迹”。

### 6.4 从 relation-only，到 richer skeleton

很多强方法最终并不只保留关系名，而是保留：

- 关系
- 方向
- 类型约束
- 子问题边界
- 终点语义

这意味着：  
如果你的最终目标只是给当前 `add_rule` 喂数据，relation-only 序列当然能用；但如果目标是长期把性能做上去，最好把规则格式升级成“关系序列 + 轻量约束”的 richer rule。

## 7. 对当前项目的直接建议

如果你现在就要在这个仓库里做一版“关系序列获取器”，我建议优先顺序如下：

1. 先做一个 `question -> top-k relation sequence` 的轻量检索/重排器。优先借鉴 Q-KGR、AMAR、GNN-RAG、S-Path-RAG。
2. 再加一个 `rule verifier / repair`。优先借鉴 RJE、CoG、RouterKGQA。
3. 如果多跳复杂问题仍然是瓶颈，再接 ToG / FiDeLiS / ORT 风格的逐步搜索。
4. 如果后面想做长期路线，再考虑 Rule-KBQA 的离线规则库，或 GraphWalker / KG-Hopper 的策略学习。

换句话说：

- 想立刻落地：先做 `检索/重排 + GCR 执行`。
- 想提高上限：再做 `分解/验证/修正`。
- 想长期积累：最后做 `规则库` 或 `策略学习`。

## 8. 总结

截至 2026-04-08，获取关系序列最有效的做法，已经不是单纯地“枚举路径”或“让 LLM 直接吐一条链”，而是：

`结构骨架生成 / 候选检索 -> 相关性重排 -> 验证或修正 -> 图上执行`

其中：

- 如果你要高精度和可执行性，逻辑形式/骨架优先方法更强。
- 如果你要低成本和高效率，检索/重排/路由方法更合适。
- 如果你要复杂多跳的上限，Agent 搜索和策略学习更有前景。
- 如果你已经有 GCR，这类图约束方法最适合作为后端执行层，而不是唯一的前端关系序列获取器。

对当前仓库最自然的升级方向，不是放弃 GCR，而是给它补一个更强的 relation planner。
