# 奖励函数重设计草案

## 1. 背景与目标

当前 `finetune/reward.py` 中的奖励函数主要由三部分构成：

- 终点实体是否命中答案实体
- 生成路径与“问题 + 答案”文本的语义相似度
- 基于固定 `expected_hops` 的绕路惩罚

结合当前训练链路，已有两个重要事实：

1. 路径生成是图约束的，候选路径来自 `Trie`，不再是完全自由生成。
2. `src/qa_prompt_builder.py` 的 `process_input()` 已经返回了 `ground_paths`，即问题实体到答案实体的最短真值路径集合。

因此，新的奖励函数应从“全局固定 hop 先验”切换到“基于样本真值路径集合的动态奖励”。

本草案的目标是：

- 保留“答案命中”这个最强信号
- 让奖励更直接地偏好“接近真实推理链”的路径
- 将“绕路惩罚”改为相对真值路径的样本级惩罚
- 将语义项从主项降为辅助项

---

## 2. 现有奖励函数的主要问题

### 2.1 固定 `expected_hops` 过于粗糙

当前做法使用全局超参数 `expected_hops`，默认值为 2。这意味着所有样本都使用同一跳数先验，但实际数据中：

- 不同问题的最短路径长度可能不同
- 不同答案实体对应的最短路径也可能不同
- 同一个样本可能存在多条最短真值路径

因此，固定 `expected_hops` 无法准确表达“这条路径是否绕路”。

### 2.2 当前语义项与任务目标不完全对齐

当前语义项比较的是：

- 生成路径文本
- “问题 + 答案”拼接出来的参考文本

但路径生成任务本质上是“生成接近真值推理链的路径”，而不是“生成与问题答案语义相关的任意文本”。

因此，更合适的监督目标应是：

- 与 `ground_paths` 的结构匹配
- 与 `ground_paths` 的弱语义匹配

### 2.3 命中答案后直接返回固定高分，无法区分路径质量

当前实现中，一旦终点命中答案实体就直接返回 `10.0`。这会导致：

- 短而准确的路径
- 冗长但最终到答案的路径

获得完全相同的奖励，无法进一步优化路径质量。

---

## 3. 重设计原则

新奖励函数建议遵循以下原则：

1. **答案命中优先**：终点到答案仍然是最重要的监督信号。
2. **结构匹配优先于语义匹配**：既然有 `ground_paths`，就优先利用路径结构信号。
3. **绕路惩罚基于真值路径动态计算**：不再使用固定 `expected_hops`。
4. **语义项保留，但仅作辅助项**：用于平滑结构匹配过硬的问题。
5. **格式项弱化**：由于已有图约束解码，格式合法性不再作为主奖励项，只保留轻量防御性检查。

---

## 4. 可直接利用的输入

新的奖励函数建议直接使用以下输入：

- `generated_path`: 模型生成路径
- `question`: 当前问题
- `a_entity`: 答案实体列表
- `ground_paths`: 最短真值路径集合

其中 `ground_paths` 已由 `src/qa_prompt_builder.py` 返回，并在 `finetune/dataset.py` 中放入样本字典，因此只需在训练器调用奖励函数时传入即可。

---

## 5. 路径表示与辅助定义

设：

- 生成路径为 `G`
- 真值路径集合为 `P = {P1, P2, ..., Pn}`

对任意路径，先解析为：

- 三元组序列：`[(h1, r1, t1), (h2, r2, t2), ...]`
- 关系序列：`[r1, r2, ...]`
- hop 数：三元组数量
- 终点实体：最后一个尾实体

辅助定义如下：

### 5.1 答案命中

设 `final_entity(G)` 为生成路径终点实体，则：

- `hit_answer(G) = 1`，若 `final_entity(G) in a_entity`
- 否则为 `0`

### 5.2 精确路径匹配

若生成路径与某条真值路径完全一致，则：

- `exact(G, Pi) = 1`
- 否则为 `0`

### 5.3 公共前缀比例

由于路径总是从问题实体出发，前缀一致性非常重要。定义：

- `prefix_len(G, Pi)`：生成路径与真值路径从起点开始连续一致的三元组数
- `prefix_ratio(G, Pi) = prefix_len(G, Pi) / len(Pi)`

### 5.4 关系序列相似度

定义关系序列的 LCS 相似度：

- `rel_sim(G, Pi) = LCS(rel(G), rel(Pi)) / len(rel(Pi))`

该项用于反映“推理模式是否接近真值路径”，即便实体层面未完全一致。

---

## 6. 路径匹配分 `R_path_match`

建议对每条真值路径 `Pi` 计算结构匹配分，然后取最大值：

`match(G, Pi) = 2.5 * exact(G, Pi) + 1.75 * prefix_ratio(G, Pi) + 1.0 * rel_sim(G, Pi)`

最终：

`R_path_match(G) = max_i match(G, Pi)`

这样设计的含义：

- 完全等于某条真值路径时，获得最高结构分
- 即使未完全匹配，只要前缀和关系模式接近，也能获得正向奖励
- 相比纯语义相似度，更直接反映“推理链是否对”

---

## 7. 绕路惩罚 `R_detour`

### 7.1 设计动机

“绕路”不应由固定的全局 `expected_hops` 决定，而应由当前样本的真值路径决定。

因此，建议先为生成路径选一个“最相近的真值路径”，再比较 hop 数差异。

### 7.2 参照路径选择

定义：

- `P* = argmax_i match(G, Pi)`

即，`P*` 是与生成路径最接近的真值路径。

如果希望更严格，也可以在终点命中答案时优先只在“终点实体相同”的真值路径中选择参照路径；若不存在，再退回到全量 `ground_paths`。

### 7.3 绕路长度定义

设：

- `hop(G)`：生成路径 hop 数
- `hop(P*)`：参照真值路径 hop 数

则：

- `extra_hops(G) = max(0, hop(G) - hop(P*))`

这表示：生成路径比最相近的真值路径“多走了几跳”。

### 7.4 绕路惩罚公式

建议：

- `R_detour(G) = -0.5 * extra_hops(G)`

说明：

- 若生成路径与最相近真值路径 hop 数相同，则不罚
- 若多走 1 跳，则扣 `0.5`
- 若多走 2 跳，则扣 `1.0`

这比固定 `expected_hops` 更准确，因为它是样本级、路径级的动态惩罚。

---

## 8. 语义辅助项 `R_semantic`

### 8.1 是否保留

建议保留，但仅作为**弱辅助项**，不再作为主奖励项。

### 8.2 比较对象

建议不再使用“生成路径 vs 问题 + 答案”作为主语义比较对象，而改为：

- `generated_path`
- `ground_paths`

即，将生成路径与真值路径文本计算嵌入相似度，再取最大值：

- `semantic(G, Pi) = cosine(emb(G), emb(Pi))`
- `R_semantic(G) = 0.5 * max_i semantic(G, Pi)`

### 8.3 语义项的作用

语义项主要用于：

- 缓解结构匹配过硬的问题
- 为“接近真值但不完全一致”的路径提供一点平滑分数
- 在结构分相近时作为次级区分信号

### 8.4 语义项的定位

建议明确：

- `R_semantic` 不是主项
- 它的权重应明显低于 `R_answer` 和 `R_path_match`

---

## 9. 推荐的总奖励公式（V1 草案）

建议使用以下总奖励：

`R_total(G) = R_answer(G) + R_path_match(G) + R_detour(G) + R_semantic(G)`

其中：

### 9.1 答案命中奖励

- 若终点命中答案实体：`R_answer = 5.0`
- 否则：`R_answer = 0`

### 9.2 路径匹配奖励

- `R_path_match = max_i [2.5 * exact(G, Pi) + 1.75 * prefix_ratio(G, Pi) + 1.0 * rel_sim(G, Pi)]`

### 9.3 绕路惩罚

- `R_detour = -0.5 * extra_hops(G)`

### 9.4 语义辅助项

- `R_semantic = 0.5 * max_i cosine(emb(G), emb(Pi))`

---

## 10. 奖励行为示例

设某个样本的真值路径之一为：

`A -> r1 -> B -> r2 -> C`

### 情况 1：完全命中真值路径

生成路径：

`A -> r1 -> B -> r2 -> C`

则通常有：

- `R_answer = 5.0`
- `exact = 1`
- `prefix_ratio = 1`
- `rel_sim = 1`
- `extra_hops = 0`
- `R_semantic` 接近上限

这是最优情况，应获得全组中最高奖励。

### 情况 2：命中答案，但比真值多绕 1 跳

生成路径：

`A -> r1 -> B -> r3 -> D -> r4 -> C`

则可能有：

- `R_answer = 5.0`
- 结构匹配中等
- `extra_hops = 1`
- `R_detour = -0.5`

应高于错误路径，但低于精确真值路径。

### 情况 3：前两跳正确，但最后没有到答案

生成路径：

`A -> r1 -> B -> r2 -> D`

则可能有：

- `R_answer = 0`
- `prefix_ratio` 较高
- `rel_sim` 较高
- 语义项中等

应得到一定正反馈，鼓励模型朝正确路径靠近，但明显低于真正命中答案的路径。

---

## 11. 不再推荐的设计

以下设计不建议继续作为主方案：

### 11.1 保留固定 `expected_hops`

原因：

- 无法适配不同样本的真实 hop 差异
- 无法处理多条真值路径并存的情况
- 不如基于 `ground_paths` 的动态 detour 计算准确

### 11.2 继续使用“问题 + 答案”作为主要语义参考文本

原因：

- 任务目标是“生成真实路径”，而不是“生成与问题答案语义相关的任意文本”
- 已有更直接的监督信号 `ground_paths`

### 11.3 终点命中后直接返回固定高分

原因：

- 会抹平路径质量差异
- 无法区分“短而准”与“长而绕但最终命中”的路径

---

## 12. 实现层面的修改建议

本草案不涉及代码修改，但后续落地时建议按如下方向调整：

1. 在训练器中把 `sample["ground_paths"]` 传入奖励函数。
2. 将 `calculate_reward()` 的签名改为接收 `ground_paths`。
3. 将 `calculate_group_rewards()` 同步改为接收 `ground_paths`。
4. 将 `expected_hops` 从主逻辑中移除，或仅作为兼容旧逻辑的 fallback。
5. 在奖励模块中新增：
   - 路径解析为三元组序列的方法
   - 前缀匹配计算方法
   - relation LCS 计算方法
   - 基于最优真值路径的 detour 计算方法
   - 基于 `ground_paths` 的语义辅助项计算方法

---

## 13. 推荐结论

建议将奖励函数改造为：

- **主项**：答案命中 + 结构路径匹配
- **辅助项**：动态 detour 惩罚 + 弱语义对齐

即：

`R_total = R_answer + R_path_match + R_detour + R_semantic`

相比现有方案，该设计的优势是：

- 更直接利用了 `ground_paths` 这个强监督信号
- detour 惩罚由样本真值动态决定，更合理
- 命中答案后仍能区分路径质量
- 语义项保留，但不会盖过结构监督

该方案适合作为下一版奖励函数的实现基线。
