# Graph-Constrained Reasoning 技术报告

## 项目概述

**项目名称**: Graph-Constrained Reasoning (GCR)  
**论文**: [Graph-constrained Reasoning: Faithful Reasoning on Knowledge Graphs with Large Language Models](https://arxiv.org/abs/2410.13080)  
**发表会议**: ICML 2025

### 核心贡献

Graph-constrained Reasoning (GCR) 是一个创新性框架,旨在解决大语言模型(LLM)在知识图谱(KG)推理中的幻觉问题。该框架通过将知识图谱的结构化信息与大语言模型的非结构化推理能力相结合,实现了零幻觉的可信推理路径生成。


## 技术架构

### 1. 核心技术组件

#### 1.1 KG-Trie 数据结构

项目实现了两种 Trie 数据结构用于高效的图索引:

- **标准 Trie** (`src/trie.py::Trie`): 基于字典的 Trie 实现
  - 支持动态添加序列
  - 提供高效的前缀查询
  - 支持 Trie 组合操作

- **Marisa Trie** (`src/trie.py::MarisaTrie`): 基于 marisa-trie 库的内存优化版本
  - 使用字符编码优化内存占用
  - 支持最多 256,001 个 token
  - 缓存首层分支以提升性能
  - 适用于大规模知识图谱索引

#### 1.2 Graph-Constrained Decoding

**核心算法** (`src/graph_constrained_decoding.py`):

该模块实现了约束解码的核心逻辑,通过以下机制确保生成的推理路径严格遵循知识图谱结构:

1. **约束标志检测**: 通过特殊的开始/结束 token 标识约束解码区域
2. **Token 过滤**: 在约束区域内,只允许生成 Trie 中存在的 token 序列
3. **无缝集成**: 通过 `prefix_allowed_tokens_fn` 接口与 HuggingFace Transformers 集成

**关键代码片段**:

```python
def allowed_tokens_fn(self, batch_id: int, sent: torch.Tensor):
    # 检查是否在约束解码区域
    constrained_flag, L_input = self.check_constrained_flag(sent)
    
    if constrained_flag:
        # 从 Trie 获取允许的 token
        allow_tokens = self.trie.get(sent.tolist()[L_input:])
        if len(allow_tokens) == 0:
            return self.all_tokens  # 回退到无约束
    return allow_tokens
```



#### 1.3 Graph Inductive Reasoning 图归纳推理 (The Judge)

这是 GCR 框架的 **Stage 2** 核心。由于 Stage 1 可能会生成多条合法的推理路径（Group Beam Search 的结果），该组件负责利用通用大模型的语义理解能力，对这些路径进行综合研判。

*   **任务目标**: 解决“多路径冲突”和“路径语义理解”问题。Stage 1 保证了路径的**真实性**，Stage 2 负责保证答案的**准确性**。
*   **流程**:
    1.  **收集**: 将 Stage 1 生成的 Top-K 条路径（如 `SwitchA -> Port1 -> Down` 和 `SwitchA -> Config -> Error`）收集起来。
    2.  **Prompt 构建**: 将这些结构化路径转化为自然语言 Prompt。
    3.  **归纳**: 调用通用 LLM（如 GPT-4 或 Llama-3）分析哪条路径最符合用户问题的意图，并生成最终答案。

### 3. 完整推理流程

#### Stage 1: Graph-Constrained Decoding

**目标**: 使用轻量级 KG-specialized LLM 生成 KG-grounded 推理路径

**流程** (`workflow/predict_paths_and_answers.py`):

1. 加载问题数据集
2. 为每个问题构建 Trie 索引(基于 DFS 收集的路径)
3. 构建提示词 (使用 `PathGenerationWithAnswerPromptBuilder`)
4. 调用 `generate_sentence()` 进行约束解码
5. 使用 beam search 生成 top-k 推理路径和候选答案
6. 保存结果到 `results/GenPaths/`

**关键特性**:

- 零幻觉: 所有生成的路径都必然存在于知识图谱中
- 高效: 使用 Trie 数据结构实现 O(log n) 复杂度的 token 过滤
- 可扩展: 支持 group-beam search 生成多样化的路径

#### Stage 2: Graph Inductive Reasoning

**目标**: 使用通用 LLM 对多个推理路径进行归纳推理

**流程** (`workflow/predict_final_answer.py`):

1. 加载 Stage 1 生成的推理路径和候选答案
2. 构建包含多个路径的提示词
3. 调用 GPT-3.5-turbo 或 GPT-4o-mini
4. 综合多个推理路径生成最终答案
5. 评估答案准确性

**优势**:

- 利用 LLM 的归纳推理能力
- 无需额外训练
- 可解释性强(提供完整推理路径)

##  前缀树

### KG 中的路径有大量共享前缀

```
路径1: Barack Obama → birthplace → Honolulu → located_in → Hawaii
路径2: Barack Obama → birthplace → Honolulu → located_in → USA
路径3: Barack Obama → birthplace → Hawaii → type → US_State
路径4: Barack Obama → birthdate → 1961
路径5: Barack Obama → profession → Politician
```

### 用普通树或者列表存储 (每个节点存完整路径)

```
需要 5 个节点，每个存储完整路径
内存: 5 × (平均长度 4) = 20 个 token 存储空间
查询: 需要检查所有 5 个节点，时间复杂度: O(N * M)，其中 N 是路径数量，M 是路径平均长度
```

### 用 Trie 存储

```
                    root
                     |
              [Barack Obama]──────────← 所有路径共享这个节点！
               /     |      \
      [birthplace][birthdate][profession]
         /    \       |           |
   [Honolulu][Hawaii][1961]  [Politician]
      /   \       |
[located_in][...]  [type]
   /    \           |
[Hawaii][USA]  [US_State]

共享的节点:
- "Barack Obama" 被5条路径共享 → 只存1次
- "birthplace" 被3条路径共享 → 只存1次
- "Honolulu" 被2条路径共享 → 只存1次

实际存储: 大约 12 个唯一节点
内存节省: 40%，时间复杂度: O(M) - M 是前缀长度
```

---
### Trie 的优势

```python
# 场景: 已生成 [Barack, Obama, →, birthplace]
# 问题: 下一步能生成什么？

# 普通树/列表:
for path in all_paths:  # 遍历 100,000 条路径
    if path[:4] == [Barack, Obama, →, birthplace]:
        candidates.add(path[4])
# 100,000 次比较

# Trie:
node = root['Barack']['Obama']['→']['birthplace']
candidates = node.children.keys()  # 直接拿到子节点
# 4 次查找 + 1 次获取子节点
```

### 3.2 子步骤: 创建约束函数

**处理:**

```python
# src/graph_constrained_decoding.py
gcr = GraphConstrainedDecoding(
    tokenizer=tokenizer,
    trie=trie,  # 步骤1构建的 Trie
    start_token_ids=None,  # 不使用 <PATH> 标记
    end_token_ids=None,
    enable_constrained_by_default=False  # 默认不约束
)

# 关键函数
def allowed_tokens_fn(batch_id: int, sent: torch.Tensor):
    """
    每生成一个 token 都会调用此函数
    
    Args:
        batch_id: beam 的索引
        sent: 已生成的完整 token 序列 [input_ids + generated_ids]
    
    Returns:
        allow_tokens: 允许生成的 token ID 列表
    """
    
    # 提取已生成的部分 (去掉 input)
    L_input = 50  # 输入长度
    generated = sent[L_input:]  # 已生成的 token
    
    # 查询 Trie
    allow_tokens = trie.get(generated.tolist())
    
    if len(allow_tokens) == 0:
        # Trie 中没有匹配的路径 → 允许所有 token (退出约束)
        return list(range(len(tokenizer)))
    
    return allow_tokens
```

#### Step 3: 长度检查与截断

**代码位置**：`PromptBuilder.check_prompt_length()`

```python
def check_prompt_length(self, prompt, list_of_paths, maximun_token):
    all_paths = "\n".join(list_of_paths)
    all_tokens = prompt + all_paths
    
    # 如果长度合适，直接返回
    if self.tokenize(all_tokens) < maximun_token:
        return all_paths
    else:
        # 超长：随机打乱并逐条添加
        random.shuffle(list_of_paths)
        new_list_of_paths = []
        
        for p in list_of_paths:
            tmp_all_paths = "\n".join(new_list_of_paths + [p])
            tmp_all_tokens = prompt + tmp_all_paths
            if self.tokenize(tmp_all_tokens) > maximun_token:
                return "\n".join(new_list_of_paths)
            new_list_of_paths.append(p)
```

**功能**：

- 防止prompt超过模型的最大context长度
- 如果路径太多，优先保留部分路径
- 随机打乱保证公平性
